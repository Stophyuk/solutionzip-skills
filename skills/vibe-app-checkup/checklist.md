# 사람이 보는 점검표

`scan.mjs`가 못 잡는 것. 항목마다 코드 · 설정에서 근거를 찾고, 없으면 사용자에게 묻는다. 결과는 **됨 · 안 됨 · 확인 필요** 셋 중 하나로 보고서에 옮긴다. 등급에 맞지 않는 항목(결제가 없는 앱의 결제 항목 등)은 '해당 없음'으로 둔다.

## 계정 · 키

- **계정 명의** — 도메인 · 클라우드 · DB · 결제(PG) · 앱 스토어 계정이 운영하는 사람(사업자) 이름인가. 왜: 결제 · 본인확인 · 스토어 계약은 사업자 명의로만 되고, 만든 사람 개인 계정에 묶이면 넘기기도 막기도 어렵다.
- **2단계 인증** — GitHub · 클라우드 · DB 대시보드 · 도메인 · 앱 관리자 계정에 켜져 있는가. 왜: 비밀번호 하나로 전부가 넘어간다.
- **공유 계정** — 여러 사람이 관리자 계정 하나를 같이 쓰지 않는가. 왜: 누가 무엇을 했는지 남지 않는다. 개인정보를 다루면 사람마다 계정과 권한 기록을 둔다(`grade.md`).
- **키 장부** — 키를 표로 정리한 문서 · 노트 · 채팅이 없는가, 키는 배포 환경 변수에만 있는가. 왜: 장부 문서가 그대로 커밋되는 일이 있다.
- **저장소 보호** — GitHub secret scanning · push protection이 켜져 있는가. 왜: 다음 실수를 푸시 단계에서 막는다.
- **끝난 프로젝트** — 안 쓰는 DB · API 키 · 테스트 서버가 살아 있지 않은가. 왜: 잊힌 프로젝트의 키는 아무도 안 보는 채로 계속 유효하다. 필요 없으면 백업 후 지운다.
- **지출 한도** — 클라우드 · AI API에 사용량 한도와 알림을 걸었는가. 왜: 키가 새거나 접속이 몰리면 청구가 먼저 온다. 한도가 몇 분 늦게 걸리는 곳도 있어, 감당할 금액보다 낮게 잡는다.

## 데이터

- **대시보드에서 만든 테이블** — Supabase 대시보드에서 직접 만든 테이블 · 정책은 SQL 파일이 없어 scan이 못 본다. 대시보드의 Security Advisor나 테이블 목록에서 RLS를 확인한다. 왜: 대시보드로만 만든 앱은 SQL 파일이 아예 없어 scan 결과가 0건으로 나온다.
- **스토리지 버킷** — 공개(public) 버킷에 신분증 · 계약서 · 개인 사진이 없는가. 왜: 공개 버킷은 주소만 알면 열린다.
- **개발이 운영 DB를 보는가** — 개발 환경이 운영 DB에 붙어 있지 않은가. 왜: 시험 데이터가 운영에 남고, 개발 PC 하나가 곧 운영 열쇠가 된다.
- **백업 · 복구 연습** — 자동 백업이 켜져 있고, 한 번이라도 복구해 봤는가. 왜: 복구해 보지 않은 백업은 쓸 수 있는지 모른다. DB를 지우면 자동 백업도 같이 사라지는 서비스가 있어, 다른 곳에도 한 벌 둔다.
- **로그에 개인정보** — `console.log(req.body)` 같은 줄이 이메일 · 전화 · 토큰을 로그에 남기지 않는가. 왜: 로그는 DB보다 덜 지켜지고 더 오래 남는다.
- **에러 화면** — 운영에서 스택 · SQL 오류 문구가 사용자 화면에 보이지 않는가. 왜: 테이블 이름 · 내부 구조가 드러난다.
- **화면에 그리는 사용자 글** — `dangerouslySetInnerHTML` · `v-html` · `innerHTML`에 사용자가 쓴 글이 들어가는가. 왜: AI가 만든 코드가 출력 이스케이프(XSS)를 특히 못 막는다는 보안 업체 측정이 있다. 사람이 직접 본다.
- **수집 항목** — 쓰지 않는 개인정보(주민번호 · 생년월일 · 상세 주소)를 받고 있지 않은가. 왜: 받는 순간 등급이 오르고 의무가 늘어난다.
- **탈퇴 · 파기** — 회원이 탈퇴하면 그 사람 데이터가 실제로 지워지는가(보관 기간이 있으면 그 뒤에). 왜: 목적이 끝난 개인정보는 복원할 수 없게 파기한다(`grade.md`).

## 결제

- **웹훅 검증** — 결제사 웹훅을 받는 곳에서 서명을 확인하는가. 서명이 없는 결제사라면 받은 결제 ID로 결제사 API에 다시 조회해 상태를 확인하는가. 왜: 가짜 "결제 완료" 요청 하나로 상품이 나간다.
- **금액 비교** — scan 경고가 없어도, 승인 직전에 서버가 저장해 둔 주문 금액과 비교하는지 직접 본다. 왜: 휴리스틱은 로직이 여러 파일로 나뉘면 놓친다.
- **두 번 처리** — 승인 · 웹훅이 두 번 와도 한 번만 처리되는가(주문 상태를 먼저 본다). 왜: 결제사는 응답이 늦으면 다시 보낸다.
- **테스트 키 → 라이브 키** — 바꾸는 일이 환경 변수만으로 끝나는가. 왜: 코드에 박힌 테스트 키 자리에 라이브 키가 그대로 들어가기 쉽다.
- **환불 · 취소** — 관리자만 부를 수 있는가. 왜: 취소 API가 열려 있으면 남의 결제를 취소한다.
- **포인트 · 충전금** — 다른 가게 · 다른 서비스에서도 쓰이는가. 왜: 여러 곳에서 쓰이는 선불 수단은 등록 문제가 붙는다(`grade.md`).

## 접근

- **권한 확인은 서버에서** — 화면 숨김 · 미들웨어만이 아니라 API · 서버 함수마다 로그인과 권한을 확인하는가. 왜: 화면을 숨겨도 API는 직접 부를 수 있고, 미들웨어만 믿다가 우회된 사례가 있다.
- **남의 데이터** — 주소의 ID만 바꿔 남의 주문 · 프로필이 열리지 않는가. 왜: 로그인 여부만 보고 주인인지는 안 보는 실수다.
- **회원가입** — 열 생각이 없는데 열려 있지 않은가. 왜: Supabase · Firebase는 가입을 막는 설정을 따로 해야 한다.
- **횟수 제한** — 로그인 · 문자 발송 · AI 호출 · 폼 접수에 횟수 제한이 있는가. 왜: 문자 · AI는 부를 때마다 돈이 나간다.
- **의존성** — `npm audit`(또는 쓰는 패키지 관리자의 같은 명령)을 한 번 돌렸는가. 왜: 알려진 취약점은 고치는 법도 알려져 있다.

## 공개 · 문서

- **개인정보 처리방침** — 회원 · 문의로 개인정보를 받으면 게시했는가. 쓰는 해외 클라우드(맡긴 곳)를 적었는가. 왜: 법정 의무이고, 해외 보관은 처리방침 공개로 동의를 갈음한다(`grade.md`).
- **저장소 공개 범위** — 공개 저장소라면 실패 0이 된 뒤에 연다. 이미 공개였다면 키 폐기가 먼저다. 왜: 비공개로 돌려도 이미 받아 간 사본은 남는다.
- **인계 한 장** — 운영을 넘길 사람이 있다면 계정 목록 · 키 이름(값 말고) · 배포 방법 · 백업 위치가 한 장에 있는가. 왜: 만든 사람만 아는 앱은 그 사람이 없으면 멈춘다.
